# 媒体管线

从 WebSocket 消息到可直接喂解码器的 Annex-B 访问单元，中间发生了什么、每一步为什么这么做。

本文说明**机制**；支撑这些结论的实测数据（多少台设备、什么现象、怎么发现的）在
[../samples/README.md](../samples/README.md)，硬约束的规范表述在
`.codebuddy/rules/media-parsing.md`，决策在 `.codebuddy/adr/ADR-0002`。

## 全链路

```
WebSocket 消息
   │  ① 协议解包（5 字节头，可能一条消息含多条协议消息，也可能没有信封）
   ▼
传输块
   │  ② RTP 判定与剥离（会话级、跨消息互证）
   ▼
容器字节（MPEG-PS）        ←── 归档样本存的就是这一层
   │  ③ PS 解复用（跨 PES 重组，一个 pack = 一个访问单元）
   ▼
Annex-B 访问单元
   │  ④ 元信息恢复（编码嗅探 / SPS 分辨率 / 关键帧 / PTS）
   ▼
OnVideoFrame(FrameMeta, []byte) → 解码器
```

实测 94 台出流设备**全部**是 MPEG-PS 容器，H.264 与 H.265 各占约一半。

## ① 协议解包

见 [protocol.md](./protocol.md)。要点：一条 WebSocket 消息可能承载多条协议消息（循环消费到
尾，否则丢帧）；也存在无信封的裸载荷；长度字段必须先扩宽再做边界检查。

## ② RTP 判定与剥离

**不是所有设备都发裸 PS**：有设备把每个 PS 分片再套一层 RTP（`80 60 ...`，version 2、PT 96、
SSRC 恒定、大量带 padding）。

判定必须**整条会话只做一次，且用两条消息互证**（同一 SSRC + 序号递增），两条**不要求相邻**
——代理会把首个 RTP 包拆成 8192 + 12 两条消息。

为什么不能逐条消息判：裸 PS 的续传消息从任意字节开始，**任意字节有 1/4 概率高两位是 `0b10`**。
42 台复测里，逐条判定让 **39/39 采集在严格结构走查中脱轨**，而帧数、关键帧数、分辨率、fps
全部正常——症状完全不可见。

剥离要把固定头、CSRC 列表、扩展头、**尾部 padding** 一起剥；padding 计数是最后一个字节且含
自身，越界即说明这不是 RTP，此时**原样返回**。实测三种处理的严格走查结果：

| 处理方式 | 走查结果 |
| --- | --- |
| 原样（RTP 头留在载荷里） | offset 0 即脱轨 |
| 只剥 12 字节固定头 | 走到 51587 脱轨 |
| **固定头 + 尾部 padding** | **走到文件尾，2671 个元素** |

RTP 载荷里装的是 MPEG-PS，**不要给它加 Annex-B 起始码**。

## ③ MPEG-PS 解复用

| 起始码 | 内容 | 处理 |
| --- | --- | --- |
| `00 00 01 BA` | pack 头 | **关闭上一个访问单元** |
| `00 00 01 BB/BC` | system header / PSM | 跳过 |
| `00 00 01 E0..EF` | 视频 PES | 去 3 字节可选头后拼进当前访问单元 |
| `00 00 01 C0..DF` | 音频 PES | 按长度跳过 |
| `00 00 01 BD` | private_stream_1 | **跳过**（见下） |

四条关键约束：

- **一个 pack 对应一个访问单元**，帧只能在下一个 pack 头到来时判定结束——天然有一帧延迟
  （实测 `firstFrame - firstByte` 中位数 29ms），**流结束必须 flush**，否则每条流稳定少最后一帧。
- **单个 NAL 会被切开跨多个 PES**，所以绝不能对未解复用的 PS 字节扫 Annex-B 起始码：既会漏
  真 NAL，又会把 PES stream_id 误判成 NAL 头，还会撞上图像数据里的伪起始码。
- **PES 可选头是 3 字节**（`flags1` / `PTS_DTS_flags` / `PES_header_data_length`）。把长度当第
  2 字节读，会把 `0x80` 的 PTS 标志当成 128 字节头长，每个 payload 被砍掉前 128 字节。实测
  `PES_header_data_length` 分布在 2..10。
- **见到第一个 pack 头之前不收 PES**。直播是从流中间接进去的（实测 22/93 台首字节不是 pack
  头，最极端的一台在第一个 pack 头前已收了 151KiB），那段字节拼出来是解不了的残帧，还会让首帧
  PTS 偏早。

### 为什么跳过 `0xBD`

94 台设备的私有流普查共 4 种记录：A 型（82 台，96 字节）**ECB 加密**、B 型（12 台，24 字节）
跨设备跨时间**恒为常量**、C 型只有 1 台设备、D 型全队列只出现一次。**没有球机坐标、转动角度
或定位信息**，与官方播放器行为一致（`h5player.min.js` 同样不解析 0xBD，PTZ 走设备 ISAPI 接口）。

它自带 PTS：当视频处理会把密文拼进码流，还会把帧时间戳取错——而帧数、关键帧数一切正常。
所以解复用器只跳过，不解析、不外露（ADR-0004）。

## ④ 元信息恢复

**SDP 是提示，码流才是事实**（ADR-0002）：

| 信息 | 来源 | 兜底 |
| --- | --- | --- |
| 容器 | `MEDIAINFO` 头 offset 8-9 | 首个载荷是否 PS 起始码（`>= 0xB9`），只判一次 |
| 编码 | `MEDIAINFO` 头 offset 10-11 | 参数集 NAL 头嗅探（H.265 认 `0x40/0x42/0x44`，H.264 认 `nal_ref_idc≠0 && type==7`） |
| 分辨率 | **不在 MEDIAINFO 里** | 一律从码流内 SPS 还原 |
| 时钟 | PS 恒为 90kHz | 不采信 SDP 的 rtpmap |

- `MEDIAINFO` 的 magic 不一定是 `IMKH`：有设备发 `HVAG`，字段布局不同，照 IMKH 解会得出垃圾值。
  组件对未知 magic 的处理是**留空而不是猜**，然后靠嗅探兜底；**嗅探结论必须写回 `MediaInfo`**，
  否则调用方看到空容器、也拿不到 90kHz 时钟。
- 全量摸底中 SDP 的 `paramsets` **94/94 为 0**——从码流还原 SPS 不是兜底路径而是主路径。
- 有设备在 video m-line 上写 `a=rtpmap:8 PCMA/8000`（音频时钟），照抄会把 25fps 算成 2.22fps。

### SPS 解析

- **先剥防竞争字节（EPB）再做位解析**。H.265 的 `general_profile_compatibility_flag` 是 32 位
  常年全 0，线上编码成 `00 00 03 00`；不剥就把 1280x720 解成 `2x1`。
- **`scaling_list()` 用 `lastScale/nextScale` 状态机读**，不能按固定长度读 se(v)：表可提前终止
  （`delta_scale` 为 0），越过 NAL 尾会让 High profile 设备分辨率恒为 0x0。
- 还原出的 SPS 要在**下一个起始码处截断**，否则会把整个关键帧当成 SPS 带出来。

### 关键帧与 PTS

- 关键帧 = 含 IDR（H.264 type 5）或 IRAP（H.265 type 16–21）。**参数集本身不是帧**。
- PTS 是 33 位、90kHz，**不从 0 开始**（实测样本首帧 PTS 分别是 1912037940 / 4040951220 /
  679651402）。`FrameMeta.HasPTS` 区分容器真实 PTS 与按到达时间合成的时间戳。

### 下游注意：从关键帧切入不一定够

两份 H.265 样本里参数集与 IDR 同属一个访问单元，任意关键帧切入都能解；但 `ps_h264_720p` 的
设备把 **SPS/PPS 单独放进前一个访问单元**，全流无 SEI。"只从关键帧开始转发"的下游在这类设备
上会丢掉参数集、解不出画面——切入时必须把紧邻其前的参数集访问单元一并带上。

## 交付给调用方的是什么

解复用后的 **Annex-B 基本流访问单元**，可直接写进 `ffmpeg` 的 stdin，不需要调用方再做任何
RTP 解包或容器解析。带元信息的回调是 Go `OnVideoFrame` / Python `on_frame`；诊断用
`OnRawVideo`（解复用**前**的容器字节，抓包归档用）与 `OnSPS`。

下游（DataStation `wails-video-ai`）**不得自行重做这一层**——DataStation `ADR-0030` 已把字节级
解析收敛到本库。理由就是本文列出的这些缺陷：它们全都不报错，只有画面是坏的，重写一遍等于把
真机摸底的结论丢掉。

## 内存复用是各自语言的事，不是解析行为

Go 侧按 128 路 profile 做过两处缓冲复用（`closeAU` 交出精确尺寸拷贝并保留累加器容量、
读循环用复用的 `bytes.Buffer` 取代 `ReadMessage` 并对交付净荷 `clone`）。**这两处不需要同步
改 Python**，已逐字节核验（2026-07-31）：

| Go | Python 对应实现 | 结论 |
| --- | --- | --- |
| `psdemux.go` `closeAU` | `hik_media.py` `_close_au` | 早已是精确尺寸拷贝：`bytes(self._au)` 交付、`self._au` 重置 |
| `client.go` 读循环 + `clone()` | `hik_ws_client.py` `_parse_ws_frame` / `receive_message` | 早已交付独立副本：净荷是 `bytes(data[...])`，剩余字节留在 `self.buffer` |

两处 Go 改动是把 Go **对齐到 Python 既有的行为**，不是反过来。三条依据：

- **交付字节完全相同。** 四份样本各自回放，把每个访问单元按 `PTS|HasPTS|len|字节` 串接取
  sha256，两侧独立计算后逐位相同（`ps_h265_720p` `8fd4cb2d…`、`ps_h265_1080p` `a1d47ce6…`、
  `ps_h264_720p` `0d7c338d…`、`ps_h264_1080p` `943a5923…`）。这比两侧各自断言帧数/关键帧数
  更强——本仓库撞过的每个解析缺陷都是"数字全对、字节是坏的"。
  > 解析行为**合法**变更时这组摘要会变，届时必须两侧同时重算并确认仍相同。
- **Go 的分配病理在 CPython 里不存在。** Go `append` 按 2 倍扩容，累加器从 nil 重新长起来会
  产生约 4 倍码流大小的中间缓冲；CPython 的 `bytearray` 扩容因子是 **1.125**，且
  `bytearray.clear()` 同样**不保留容量**（实测 `getsizeof` 100057 → 57），所以
  `self._au = bytearray()` 与任何"复用"写法在 CPython 里等价，改了也换不来 Go 那笔收益。
- **`clone()` 在 Python 里没有对应物可加。** `_parse_ws_frame` 交出去的是不可变 `bytes`，与
  读缓冲彻底脱钩；实测把 `self.buffer` 原地清零，已交付的净荷不受影响。Go 需要 `clone` 只是
  因为它改用了会被下次读覆盖的复用缓冲。

推论（供后续改动参照）：**分配策略属于单侧工程设施，与"两侧同时改"的解析行为不是一回事。**
判据只有一条——是否改变交付给调用方的字节；不改变就不必同步，改变就必须同步且两侧回放样本。
