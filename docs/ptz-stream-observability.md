# 云台转动时，码流里能不能看出来

问题只有一句：**球机正在转的那几百毫秒，码流里有没有可提取的"正在转"信号。**

`samples/README.md` 里 94 台设备的 `0xBD` 普查回答的是另一个问题——**静置**时私有流里有什么。
那是基线，不是答案：没有人在转动过程中看过同一条流。这份文档记录的是补上这一步的受控差分实测。

## 结论

| 层 | 看什么 | 结论 |
| --- | --- | --- |
| ① WS 文本通道 | `errorCode` / `sdp` 之外的 JSON | **没有**。25 分钟码流、64 次转动，一条都没出现过 |
| ② WS 二进制未知类型 | `0x01`~`0x06` / `0x40` / `0x41` 之外的包类型 | **没有**。只收到 `0x40`，未知类型 0 条，服务端 keepalive 0 条 |
| ③ `0xBD` 私有流 | 转动前后记录是否变化 | **没有**。A 型密文照旧每关键帧 1 条，B 型常量一个字节不变，无新记录型 |
| ④ 码流内 SEI | `user_data_unregistered` 等 | **没有**。半数设备只发一种 4 字节厂商 SEI，取值与转动无关 |
| ⑤ 编码器间接信号 | 访问单元大小、关键帧节奏 | **有信号，但不可用作判据**——见下面的误报分析 |

一句话：**转动这件事在码流里唯一留下的痕迹是"画面整体变了"，而这与"有人从镜头前走过"
是同一种痕迹。** 想知道云台在不在转，只能问设备控制接口，码流侧做不到。

## 为什么必须做受控差分

同一台设备、同一条流，比较"转动窗口内"和"窗口外"，逐层对齐。这是唯一能把码流里的异常
归因到转动的办法：不同设备之间的码率、场景、GOP 完全没有可比性，同一台设备不同时段的
场景活跃度也天差地别（实测同一台设备两次采集的非关键帧中位数能差 1.9 倍）。

工具是 `go-client/e2e/ptztap`，单进程内串起全过程：取 playUrl → 建连 → 采集基线 →
**在记录下的确切时刻**发 `movePtzTimed` → 继续采集 → 反向复位。所有样本的时间戳和 PTZ
请求的收发时刻用同一个时钟，否则任何"窗口内"的说法都不成立。

采集规模：

| | |
| --- | --- |
| 设备 | 4 台（A/C/D 为 H.265，B 为 H.264；全部 PS 容器、25fps、GOP 约 2s） |
| 采集 | 19 次（11 次带 PTZ，8 次静置对照），累计 25.3 分钟码流、38468 个访问单元 |
| 转动 | 64 次，方向轮转 左/右/上/下，每轮反向复位 |
| 对照组 | 同样时长、同样分析、**完全不发 PTZ**，用来量误报 |

设备侧特征刻意选得不一样，以覆盖不同的 `0xBD` 类型：

| 设备 | 编码 | `0xBD` 记录型 | SEI |
| --- | --- | --- | --- |
| A | H.265 | A 型 96B | 有（`payloadType 229`） |
| B | H.264 | A 型 96B | 无 |
| C | H.265 | A 型 96B | 有（`payloadType 229`） |
| D | H.265 | A 型 96B + B 型 24B | 无 |

普查里的 C 型（92B）/ D 型（36B）在这一轮 12 台在线设备的探测中一台都没复现，本轮未覆盖。

### 平台侧的转动时序（决定了"窗口"有多长）

`movePtzTimed` 回包自带时序字段，64 次调用 `stop_success` 全为 true：

- **启动延迟中位数 401ms**（289~601ms）。请求 `duration_ms=240` 时，启动延迟已经超过请求
  时长，平台把实际转动压到下限 50ms（60/64 次如此）；请求 900ms 时实际转动 384~525ms。
- 所以**"转 240ms"实际只转了几十毫秒**，但码流里的扰动持续 1.5~2s——云台加减速加上停止
  指令的往返，比指令本身长得多。分析窗口取 `[平台报告的启动时刻, 停止调用返回]`，并封顶
  3s：观测到过一次停止调用 12.5s 才返回，那 12 秒球机早就停了，不能算进转动窗口。

## ① / ② WebSocket 通道：一条都没有

组件此前对这两类消息是**静默丢弃**：文本消息只认 `errorCode` 和 `sdp`，二进制只认
`0x01`~`0x06` / `0x40` / `0x41`，其余直接 return，日志里连痕迹都没有。丢弃是对的，但
"没日志"意味着**无法证明确实没有东西**——这次先给丢弃分支补上 Verbose 日志（只加日志，
不改任何解析语义），再统计：

| | 全部 19 次采集合计 |
| --- | --- |
| 文本消息（非 `errorCode`/`sdp`） | **0** |
| 文本消息（非 JSON） | **0** |
| 未知二进制类型 | **0** |
| 服务端 keepalive (`0x06`) | **0** |
| 视频载荷 (`0x40`) | 59934 |
| 音频载荷 (`0x41`) | 0 |

转动窗口内外都是这个数。**代理在转动期间不会向客户端推送任何额外消息**——它压根就没有
这条通路。

## ③ `0xBD` 私有流：结构和节律都没变

按 MPEG-PS 逐元素步进（不是扫字节，见 `docs/media-pipeline.md`）取出所有 `private_stream_1`
记录，转动窗口内外对比：

**A 型（96 字节，4 台设备全都有，共 776 条）**

- **每个关键帧恰好 1 条**：19 次采集里 17 次记录数与关键帧数完全相等，另外 2 次差 1
  （采集首尾截断）；776 条里 774 条落在某个关键帧的 100ms 内。转动**不会**改变这个节律，
  也不会插入新记录。
- 16 字节固定头 `00 02 00 17 00 01 80 00 00 ff 00 00 e0 f1 f0 50` 在 4 台设备上完全一致，
  与普查结论一致。
- 后 80 字节**每条都不同**（449 条互不重复），转动时和静置时一样不可预测——没有任何字节
  位置在转动时呈现规律。
- 顺带独立复现了 ECB 的判据：**209/209 条记录的第 3、4 个 16 字节密文块相同**，且位置固定。
  明文里有两个相同的 16 字节字段，转动与否都相同。没有设备密钥就到此为止（ADR-0004）。

**B 型（24 字节，设备 D，共 3177 条）**

- 以 **10.9 条/秒**（间隔中位数 92ms）稳定发送，转动期间频率不变。
- 载荷 `00030005 0001800000ff0000 ffff0401008187808438ff02` 在全部 3177 条里**一个字节都
  没变**，包括 900ms 长转动期间。普查说它是常量，转动也没能让这个常量破掉。

**结论：`0xBD` 在转动时既没有新记录型，也没有长度/频率变化，A 型密文与静置时同样不可读。**

## ④ SEI：只有一种厂商 SEI，与转动无关

在解复用后的基本流里扫 Annex-B NAL（先剥防竞争字节再解析 SEI payload，`0xFF` 续读形式
的 `payloadType`/`payloadSize` 都要处理）：

- **两台 H.265 设备（A、C）各只发一种 SEI**：`nal_type=39`（prefix SEI）、
  `payloadType=229`、载荷 4 字节，共 416 条。
- **`user_data_unregistered`（H.264 type 5 / H.265 同号）从未出现**；H.264 设备 B 在 2133
  个访问单元里一个 SEI 都没有。
- 4 字节载荷形如 `XX YY 00 00`，末两字节恒为 0。设备 A 上 `XX == YY` 恒成立（99/99 个不同
  取值），设备 C 上两字节独立。取值随每个关键帧变化、不递增、不重复出现固定值——像校验值
  或随机数，**不是计数器，也不是状态字**。
- 每个关键帧恰好一条：转动窗口内的条数就等于窗口内的关键帧数，静置时同理。**转动没有让
  它多发、少发或改变取值分布。**

（本层是唯一需要看载荷字节才能下结论的：只统计条数会得到"转动时也有 SEI"这种毫无信息量的
结果，条数相等恰恰说明它跟着关键帧走而不是跟着云台走。）

## ⑤ 编码器间接信号：有信号，但不能当判据

云台一转，整幅画面位移，帧间预测失效，P 帧膨胀。这一层不需要解码，只看访问单元字节数
的时间序列。

### 统计量

**窗口内最大非关键帧 ÷ 紧邻的前 8 秒非关键帧中位数**（窗口 1.8s，步进 0.2s）。两个性质是
必需的：

- **相对**——4Mbps 的工地和一堵静止的墙之间没有共同的绝对尺度，只有设备自己的近期历史
  是公平参照；
- **因果**——基线严格取自窗口之前。拿整段采集的静置中位数当分母是事后诸葛亮，线上消费者
  算不出那个数。

关键帧被排除在外：GOP 是固定 2s 周期的，**转动不会触发额外的 I 帧插入**（每个转动窗口内
恰好 1 个关键帧，与静置窗口一样），把 I 帧算进去只会让分子被 GOP 相位主导。

### 结果

64 次真实转动 vs 815 秒静置候选窗口（含对照组和实验组的静置段）：

| 阈值 | 检出 | 误报 |
| --- | --- | --- |
| 3x | 53/64（83%） | 4.20 次/分钟 |
| 4x | 52/64（81%） | 3.17 次/分钟 |
| **5x** | **44/64（69%）** | **1.47 次/分钟** |
| 6x | 34/64（53%） | 1.03 次/分钟 |
| 8x | 21/64（33%） | 0.66 次/分钟 |
| 10x | 17/64（27%） | 0.44 次/分钟 |
| 15x | 9/64（14%） | 0.37 次/分钟 |

没有任何一个阈值能同时做到高检出和低误报。更要命的是**分设备**看：

| 设备 | 转动窗口统计量 min / 中位 / max |
| --- | --- |
| A | 4.5 / 6.3 / 9.5 |
| B | 4.4 / 6.0 / 15.7 |
| C | **1.6** / **2.7** / 9.0 |
| D | 5.8 / 15.2 / 38.6 |

设备 D 的中位数是设备 C 的 5.6 倍。**同一个阈值在 D 上检出 100%，在 C 上检出 0%**——C 的
一半转动连 2x 都到不了（视场、焦距、场景纹理决定了同样角速度下画面变化量差一个数量级）。
跨设备统一阈值不存在，逐设备标定则需要对每台设备做一次带 PTZ 的现场标定，而这正是想避免的。

### 误报分析：人走过和云台转是同一种信号

这是决定性的一条。**对照组里完全没有发 PTZ 指令，统计量照样能飙到 54.5x**：

| 采集 | 是否发 PTZ | 静置段最大统计量 |
| --- | --- | --- |
| 对照组 · 设备 D | 否 | **54.5x** |
| 对照组 · 设备 D（另一次） | 否 | 53.6x |
| 对照组 · 设备 B | 否 | 29.7x |
| 全部 64 次真实转动的最大值 | 是 | 38.6x |

**静置对照组里最大的一次自然场景事件（54.5x），比 64 次真实转动中最强的一次（38.6x）还大。**
这不是阈值调得不好，是这个统计量物理上分不开两件事：它测的是"帧间预测失效的程度"，而
一辆渣土车从镜头前开过、一片强光变化、雨刷扫过，与云台转动在编码器眼里是同一件事。

设备 B 的对照组尤其说明问题：完全没转，6 个虚拟窗口里有 3 个超过 3x、1 个到 7.2x，43 秒
静置里有 3 次超过 8x 的误报。工地摄像机的场景本来就在动。

### 如果还是要用

只有在**已知云台何时被下发指令**的前提下，这个统计量才有意义——那时它不是检测器，是
**验证器**：确认那条 PTZ 指令确实让画面动了（`stop_success=true` 只代表平台收下了指令）。
用法是：以指令时刻为中心取 [启动延迟, +3s] 窗口，统计量 ≥ 5x 视为"确实动了"，低于 2x 值得
怀疑指令没有落到设备上。这条路径需要控制侧的时间戳，本组件拿不到，也不该拿。

## 复现

```sh
HIK_OA_BASE=https://example.com/api.php HIK_OA_TOKEN=auth_token \
  go run ./e2e/ptztap -ipc <ipc_id> -rounds 3 -baseline 10s -post 10s \
                      -duration-ms 240 -dirs 2,3,0 -out /tmp/ptz.json

# 对照组：同样的时间表、同样的分析，一条 PTZ 指令都不发
HIK_OA_BASE=... HIK_OA_TOKEN=... go run ./e2e/ptztap -ipc <ipc_id> -control -out /tmp/null.json
```

工具每次运行都会打印五层的逐层结论，包括第 ⑤ 层检测器在**本次采集自己的静置段**上的误报
计数——上面表格里的数字就是把 19 次运行的这些输出汇总起来的，没有额外的分析脚本。

跑之前注意两件事：**token 一次性、几分钟过期**，所以取 playUrl 和建连必须在同一个进程里
连着做；**每轮都会反向复位**，进程中途死掉最多让球机偏一次 240ms 的量。

## 边界

这次调查**没有**改变组件边界，也不应该被当成改变边界的理由：

- 解复用器照旧**跳过** `0xBD`，不解析、不外露；
- 客户端照旧**丢弃**未知消息类型，只是丢弃时会在 Verbose 下留一行日志；
- 组件不做 PTZ 控制、不做 `0xBD` 解密、不提供"云台是否在转"的判断。

第 ⑤ 层的信号真实存在，但它是**场景变化**的信号而不是**云台状态**的信号，把它包装成
`IsPanning()` 之类的 API 会给调用方一个 30% 漏报、每分钟一次误报的假承诺。相关边界表述见
[ADR-0004](../.codebuddy/adr/ADR-0004-component-scope-boundary.md)。
