# 码流样本库

用于 `hik_ws_client` 组件的离线调试与研究。线上测试链接是一次性的、分钟级过期，
拿不到第二次；每次拿到新链接都必须**当场采集并归档**，样本才是可复现问题的唯一依据。

## 采集

```bash
cd go-client
go run ./e2e/probe -url 'wss://<host>:<port>/proxy/[<ip>]:<port>/openUrl/<token>' -dur 20s
```

`probe` 一次连接内同时完成分析与归档，不要拆成两次运行——第二次必然
`errorCode 28316423`（URL 已失效）。

## 目录约定

按**容器 + 编码 + 分辨率**分类，一种组合一个目录，例如 `ps_h265_720p/`、
`ps_h265_1080p/`、`ps_h264_1080p/`。目录名由 `probe` 从 MEDIAINFO 与码流内 SPS
自动推导（同容器同编码的不同分辨率因此不会互相覆盖），也可用 `-name` 覆盖。

每个目录内：

| 文件 | 内容 |
| --- | --- |
| `stream.ps` / `stream.bin` | 解复用**前**的容器原始字节，唯一不可再生的材料 |
| `stream.sdp` | realplay 返回的 SDP 原文（含 MEDIAINFO 头） |
| `sps.bin` | 命中的第一个 SPS NAL，分辨率解析回归用 |
| `summary.txt` | 该次采集的容器/编码/分辨率/帧数/关键帧/PTS/fps 摘要 |

**样本里不得出现任何部署信息**：主机名、代理内网地址、openUrl token、设备名一律
不写入归档文件。`probe` 的摘要因此完全不记录源 URL——它对分析码流毫无价值，却是
提交进仓库后擦不掉的东西。归档前用 `grep -ri '<你的域名>' samples/` 自查一次。

只存容器原始字节，不存解复用后的基本流：后者由组件从前者完整再生，且 MPEG-PS
本身是标准容器，ffmpeg 可直接读，没必要在仓库里再放一份几 MB 的派生产物。

```bash
ffprobe -v error -show_streams samples/ps_h265_720p/stream.ps
```

## 回归复用

`go-client/sample_replay_test.go` 把样本重放进解复用器，断言帧数、关键帧数、
PTS 单调性、每个访问单元以起始码开头、以及从码流内 SPS 还原的分辨率；样本缺失时
自动 skip。这样每次改解析逻辑都会被真实设备字节校验一次——合成用例只能证明
解析器自洽，证明不了它跟真机一致。

## 已知码流特征（实测结论，非文档推测）

三份样本的实测值：

| | `ps_h265_720p` | `ps_h265_1080p` | `ps_h264_720p` |
| --- | --- | --- | --- |
| 编码 | H.265 | H.265 | H.264 |
| 分辨率 | 1280x720 | 1920x1080 | 1280x720 |
| 帧数 / 关键帧 | 611 / 25 | 614 / 13 | 655 / 26 |
| GOP | 25 | 50 | 25 |
| 原始字节 | 5,301,664 | 2,944,632 | 4,053,224（去 RTP 后） |
| fps（PTS 推算） | 24.93 | 25.01 | 26.04 |
| 视频 PES / 音频 PES | 2163 / 32 | 1219 / 646 | 655 / 1257 |
| 线上封装 | 裸 PS | 裸 PS | **RTP over WS** |
| MEDIAINFO magic | `IMKH` | `IMKH` | **`HVAG`（无法解码）** |
| SDP rtpmap | `0 /0`（空） | `8 PCMA/8000` | `0 /0`（空） |

两份 H.265 样本 NAL 构成一致：VPS / SPS / PPS / SEI / IDR_W_RADL 各等于关键帧数，
其余为 TRAIL_R —— **参数集与 IDR 同属一个访问单元**，任意关键帧处切入都能解码。

`ps_h264_720p` 不是这样，实测 655 个访问单元只有三种形态：

| 访问单元内容 | 数量 | `AnalyzeFrame` 判关键帧 |
| --- | --- | --- |
| SPS(7) + PPS(8) | 26 | false |
| IDR(5) | 26 | true |
| 非 IDR 片(1) | 603 | false |

**参数集单独成一个 PS pack，排在 IDR 的前一个访问单元**，且全流没有 SEI。因此
"只从关键帧开始转发"的下游会丢掉 SPS/PPS 而解不出画面——从关键帧切入时必须把
紧邻其前的参数集访问单元一并带上。`AnalyzeFrame` 保持只认 IDR 是对的：参数集
本身不是帧，判定权归调用方。

- **容器是 MPEG-PS，不是裸 annex-b。** 二者只声明在 SDP 的
  `a=Media_header:MEDIAINFO=<hex>` 里：40 字节 IMKH 头，offset 8-9 为容器
  （`02 00` = PS），offset 10-11 为编码（`05 00` = H265）。
- **MEDIAINFO 的 magic 不一定是 `IMKH`，不能假定能解码。** `ps_h264_720p` 的设备
  发的是 `48564147`（`HVAG`），字段布局与 IMKH 不同，照 IMKH 解会得出垃圾值。
  组件对未知 magic 的处理是**留空而不是猜**：容器由首个载荷是否 `00 00 01 ba`
  嗅探，编码由码流内 NAL 头嗅探（`sniffCodec`：H.265 认 `0x40/0x42/0x44`，
  H.264 认 `nal_ref_idc≠0 && type==7`）。SDP 是提示，码流才是事实。
- **容器只能在第一个载荷上判定一次。** 后续消息多是 PES 续传，不以 `00 00 01 ba`
  开头，逐消息嗅探会在流中途把自己判成非 PS。
- **码流可能被 RTP 二次封装**，见下节。
- **MEDIAINFO 头里没有分辨率**，必须从码流内的 SPS 还原。
- **一个 PS pack 对应一个访问单元**，所以帧只能在下一个 pack 头到来时才判定结束，
  天然有一帧延迟；流结束时必须 flush，否则丢最后一帧。
- **单个 NAL 会被切开跨多个 PES 包**，因此绝不能对未解复用的 PS 字节做 annex-b
  起始码扫描——既会漏掉真 NAL，又会把 PES stream_id 误判成 NAL 头。
- **PES 可选头是 3 字节**（`flags1` / `PTS_DTS_flags` / `PES_header_data_length`）。
  把长度当成第 2 字节读，会把 `0x80` 的 PTS 标志当成 128 字节头长：每个 PES payload
  被砍掉前 128 字节、PTS 也早解一字节。症状极隐蔽——帧数、关键帧数、码率看着都正常。

  样本实测头部（2147 个视频 PES）：`flags1` 只取 `0x8C`/`0x88`（高两位恒为 `10`），
  `PES_header_data_length` 分布在 2..10，带 PTS 时为 8（5 字节 PTS + 3 字节 `0xFF` 填充）。
  例如首个 PES 头是 `8c 80 08 23 c7 dd c4 69 ff ff fc`，其后紧跟 `00 00 00 01 40 01`（VPS）。
  按错误解法，这个包会跳过 128 字节，直接把整个 VPS 连同后面的内容一起吞掉。
- **H.265/H.264 SPS 必须先去除防竞争字节（EPB）再做位解析。** H.265 的
  `general_profile_compatibility_flag` 是 32 位常为 0 的字段，天然构成 `00 00 00 00`，
  在线上会被编码成 `00 00 03 00 ...`；不剥离就会导致后续所有字段错位，实测把
  1280x720 解析成 `2x1`。

  样本里真实的 SPS（`sps.bin`，37 字节）：
  `00 00 01 42 01 01 01 60 00 00 03 00 b0 00 00 03 00 00 03 00 5d a0 02 80 80 2d ...`
  —— 三处 `00 00 03` 转义全部落在 profile 区，正是错位的来源。
- PTS 是 33 位、90kHz，且**不从 0 开始**（三份样本首帧分别是 1912037940、
  4040951220、679651402），不能假设起点为 0。
- **PS 的时钟恒为 90kHz，不能采信 SDP 的 rtpmap。** `ps_h265_1080p` 的设备在
  video m-line 上写的是 `a=rtpmap:8 PCMA/8000`（音频时钟），照抄会把 25 fps 的流
  算成 2.22 fps。MPEG-PS 的 PTS 单位由容器规范固定，与 rtpmap 无关。
- **同一路 PS 里会混有音频 PES**（`ps_h265_1080p` 有 646 个，stream_id `0xC0`
  段）。解复用必须按长度跳过它们，只把 `0xE0..0xEF` 的载荷拼进视频访问单元；
  这份样本是第一份音频占比可观的真机流，正好验证了这条路径。

## RTP 二次封装（`ps_h264_720p` 实测）

**不是所有设备都直接发裸 PS。** 这台设备把每个 PS 分片再套一层 RTP：WebSocket
消息以 `80 60 ...` 开头（version 2、PT 96），2031 个包里 1728 个带 padding、
1886 个带 marker、SSRC 全程为同一个值，无 CSRC、无扩展头。

危险在于**症状完全不可见**：把 RTP 头留在载荷里，PS 解复用器靠 resync 依然能跑
出 655 帧 / 26 关键帧 / 1280x720，和正确结果一模一样。只有对基本流做 sha256
才发现两者从 offset 8054 起就不同——145 个包中段的 RTP 头被当成图像数据写进了
PES 载荷，画面是坏的而计数是对的。

判定用的是**严格 PS 结构走查**（只按规范逐个 pack/system/PSM/PES 前进，不允许
任何 resync）：

| 处理方式 | 走查结果 |
| --- | --- |
| 原样（RTP 头在内） | offset 0 即脱轨 |
| 只剥 12 字节固定头 | 走到 51587 脱轨 |
| **剥固定头 + 尾部 padding** | **走到文件尾，2671 个元素** |

2671 = 655 pack + 52 system + 52 PSM + 655 视频 PES + 1257 音频 PES。
只有两者都剥才字节级正确，所以 `rtp.go` 的 `rtpPayload` 两件都做（并按规范处理
CSRC 列表与扩展头长度）。padding 计数是最后一个字节且**含自身**，越界就说明这
根本不是 RTP，此时原样返回，裸 PS / 裸 annex-b 才不会被误剥。

归档的 `stream.ps` 是**去封装后**的干净 MPEG-PS（4,053,224 字节，`ffprobe` 可直
接读）：RTP 是传输层的事，样本要留的是容器层的真相。

## 踩坑记录

- **自建 mock 要照着真实字节写。** 单元测试的构造 helper 一旦和实现犯同一个错误
  （PES 头长度取错位置），测试全绿而线上全错。涉及线格式的断言要手写字节，不要
  复用 helper。
- **"帧数对、关键帧对"不等于解析正确。** 上面的 PES 截断问题、RTP 头未剥问题，在
  摘要里都完全看不出来（后者连分辨率都是对的），只有对照 `ffprobe`、逐字节回放归档
  样本、或做严格结构走查才能发现。这正是要留样本的原因。
- **SDP 只是提示，码流才是事实。** 前两台设备的 MEDIAINFO 能解，就默认了它总能解；
  第三台换成 `HVAG` 头，整条链路退化成"未知容器 + 未知编码"。凡是设备自报的元数据，
  都要有一条从码流本身推导的兜底路径。
- **一次连接只做一件事的工具设计是错的。** token 分钟级过期，"先分析再抓包"的两次
  运行第二次必然失败，白白烧掉一个链接。`probe` 因此把两件事合并进同一次连接。
