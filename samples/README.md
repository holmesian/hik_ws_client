# 码流样本库

用于 `hik_ws_client` 组件的离线调试与研究。线上测试链接是一次性的、分钟级过期，
拿不到第二次；每次拿到新链接都必须**当场采集并归档**，样本才是可复现问题的唯一依据。

## 取样本（Git LFS）

`*.ps` / `*.bin` 由 Git LFS 管理（见仓库根的 `.gitattributes`），普通 clone 只会拿到
指针文件。要跑回放测试先装 LFS 再拉内容：

```bash
git lfs install
git lfs pull
```

`sample_replay_test.go` 认得未拉取的指针文件并 skip（否则它会以"结构在 offset 0
脱轨"这种看不懂的方式失败）。但 skip 意味着**没拉内容就等于没跑回放回归**，CI 里
必须显式 `git lfs pull`。

## 采集

```bash
cd go-client
go run ./e2e/probe -url 'wss://<host>:<port>/proxy/[<ip>]:<port>/openUrl/<token>' -dur 20s
```

`probe` 一次连接内同时完成分析与归档，不要拆成两次运行——第二次必然
`errorCode 28316423`（URL 已失效）。

## 目录约定

按**容器 + 编码 + 分辨率**分类，一种组合一个目录，例如 `ps_h265_720p/`、
`ps_h265_1080p/`、`ps_h264_1080p/`。目录名由 `probe` 从 MEDIAINFO 与码流内 SPS
自动推导（同容器同编码的不同分辨率因此不会互相覆盖），也可用 `-name` 覆盖。

每个目录内：

| 文件 | 内容 |
| --- | --- |
| `stream.ps` / `stream.bin` | 解复用**前**的容器原始字节，唯一不可再生的材料 |
| `stream.sdp` | realplay 返回的 SDP 原文（含 MEDIAINFO 头） |
| `sps.bin` | 命中的第一个 SPS NAL，分辨率解析回归用 |
| `summary.txt` | 该次采集的容器/编码/分辨率/帧数/关键帧/PTS/fps 摘要 |

**样本里不得出现任何部署信息**：主机名、代理内网地址、openUrl token、设备名一律
不写入归档文件。`probe` 的摘要因此完全不记录源 URL——它对分析码流毫无价值，却是
提交进仓库后擦不掉的东西。归档前用 `grep -ri '<你的域名>' samples/` 自查一次。

只存容器原始字节，不存解复用后的基本流：后者由组件从前者完整再生，且 MPEG-PS
本身是标准容器，ffmpeg 可直接读，没必要在仓库里再放一份几 MB 的派生产物。

```bash
ffprobe -v error -show_streams samples/ps_h265_720p/stream.ps
```

## 回归复用

`go-client/sample_replay_test.go` 把样本重放进解复用器，断言帧数、关键帧数、
PTS 单调性、每个访问单元以起始码开头、以及从码流内 SPS 还原的分辨率；样本缺失时
自动 skip。这样每次改解析逻辑都会被真实设备字节校验一次——合成用例只能证明
解析器自洽，证明不了它跟真机一致。

## 已知码流特征（实测结论，非文档推测）

四份样本覆盖 `{H.264, H.265} × {720p, 1080p}`——这正是全量摸底里 94 台出流设备的
全部形态（见下文），没有第五种组合。实测值：

| | `ps_h265_720p` | `ps_h265_1080p` | `ps_h264_720p` | `ps_h264_1080p` |
| --- | --- | --- | --- | --- |
| 编码 | H.265 | H.265 | H.264 | H.264 |
| 分辨率 | 1280x720 | 1920x1080 | 1280x720 | 1920x1080 |
| 帧数 / 关键帧 | 611 / 25 | 614 / 13 | 655 / 26 | 199 / 8 |
| GOP | 25 | 50 | 25 | 25 |
| 原始字节 | 5,301,664 | 2,944,632 | 4,053,224（去 RTP 后） | 1,893,104 |
| fps（PTS 推算） | 24.93 | 25.01 | 26.04 | 25.01 |
| 视频 PES | 2147 | 1203 | 655 | 752 |
| 音频 PES | 0 | 614 | 1257 | 0 |
| 私有 PES（0xBD） | 25（A） | 13（A） | 0 | **88（A×8 B×79 D×1）** |
| 线上封装 | 裸 PS | 裸 PS | **RTP over WS** | 裸 PS |
| MEDIAINFO magic | `IMKH` | `IMKH` | **`HVAG`（无法解码）** | `IMKH` |
| SDP rtpmap | `0 /0`（空） | `8 PCMA/8000` | `0 /0`（空） | `0 /0`（空） |

PES 计数是按严格结构走查逐个元素数出来的。此前表里的 `2163 / 32`、`1219 / 646`
是用扫 `00 00 01 xx` 起始码数出来的，会把落在图像数据里的伪起始码算进去——这份
README 自己在别处警告过这件事，计数本身却踩了同一个坑，现已按走查结果订正。

`ps_h264_1080p` 是唯一带 B / D 型私有记录的样本，也是唯一一份带 D 型（全队列只
出现过一次）的采集；私有流分析见后文。

两份 H.265 样本 NAL 构成一致：VPS / SPS / PPS / SEI / IDR_W_RADL 各等于关键帧数，
其余为 TRAIL_R —— **参数集与 IDR 同属一个访问单元**，任意关键帧处切入都能解码。

`ps_h264_720p` 不是这样，实测 655 个访问单元只有三种形态：

| 访问单元内容 | 数量 | `AnalyzeFrame` 判关键帧 |
| --- | --- | --- |
| SPS(7) + PPS(8) | 26 | false |
| IDR(5) | 26 | true |
| 非 IDR 片(1) | 603 | false |

**参数集单独成一个 PS pack，排在 IDR 的前一个访问单元**，且全流没有 SEI。因此
"只从关键帧开始转发"的下游会丢掉 SPS/PPS 而解不出画面——从关键帧切入时必须把
紧邻其前的参数集访问单元一并带上。`AnalyzeFrame` 保持只认 IDR 是对的：参数集
本身不是帧，判定权归调用方。

- **容器是 MPEG-PS，不是裸 annex-b。** 二者只声明在 SDP 的
  `a=Media_header:MEDIAINFO=<hex>` 里：40 字节 IMKH 头，offset 8-9 为容器
  （`02 00` = PS），offset 10-11 为编码（`05 00` = H265）。
- **MEDIAINFO 的 magic 不一定是 `IMKH`，不能假定能解码。** `ps_h264_720p` 的设备
  发的是 `48564147`（`HVAG`），字段布局与 IMKH 不同，照 IMKH 解会得出垃圾值。
  组件对未知 magic 的处理是**留空而不是猜**：容器由首个载荷是否 `00 00 01 ba`
  嗅探，编码由码流内 NAL 头嗅探（`sniffCodec`：H.265 认 `0x40/0x42/0x44`，
  H.264 认 `nal_ref_idc≠0 && type==7`）。SDP 是提示，码流才是事实。
- **容器只能在第一个载荷上判定一次。** 后续消息多是 PES 续传，不以 `00 00 01 ba`
  开头，逐消息嗅探会在流中途把自己判成非 PS。
- **码流可能被 RTP 二次封装**，见下节。
- **MEDIAINFO 头里没有分辨率**，必须从码流内的 SPS 还原。
- **一个 PS pack 对应一个访问单元**，所以帧只能在下一个 pack 头到来时才判定结束，
  天然有一帧延迟；流结束时必须 flush，否则丢最后一帧。
- **单个 NAL 会被切开跨多个 PES 包**，因此绝不能对未解复用的 PS 字节做 annex-b
  起始码扫描——既会漏掉真 NAL，又会把 PES stream_id 误判成 NAL 头。
- **PES 可选头是 3 字节**（`flags1` / `PTS_DTS_flags` / `PES_header_data_length`）。
  把长度当成第 2 字节读，会把 `0x80` 的 PTS 标志当成 128 字节头长：每个 PES payload
  被砍掉前 128 字节、PTS 也早解一字节。症状极隐蔽——帧数、关键帧数、码率看着都正常。

  样本实测头部（2147 个视频 PES）：`flags1` 只取 `0x8C`/`0x88`（高两位恒为 `10`），
  `PES_header_data_length` 分布在 2..10，带 PTS 时为 8（5 字节 PTS + 3 字节 `0xFF` 填充）。
  例如首个 PES 头是 `8c 80 08 23 c7 dd c4 69 ff ff fc`，其后紧跟 `00 00 00 01 40 01`（VPS）。
  按错误解法，这个包会跳过 128 字节，直接把整个 VPS 连同后面的内容一起吞掉。
- **H.265/H.264 SPS 必须先去除防竞争字节（EPB）再做位解析。** H.265 的
  `general_profile_compatibility_flag` 是 32 位常为 0 的字段，天然构成 `00 00 00 00`，
  在线上会被编码成 `00 00 03 00 ...`；不剥离就会导致后续所有字段错位，实测把
  1280x720 解析成 `2x1`。

  样本里真实的 SPS（`sps.bin`，37 字节）：
  `00 00 01 42 01 01 01 60 00 00 03 00 b0 00 00 03 00 00 03 00 5d a0 02 80 80 2d ...`
  —— 三处 `00 00 03` 转义全部落在 profile 区，正是错位的来源。
- PTS 是 33 位、90kHz，且**不从 0 开始**（三份样本首帧分别是 1912037940、
  4040951220、679651402），不能假设起点为 0。
- **PS 的时钟恒为 90kHz，不能采信 SDP 的 rtpmap。** `ps_h265_1080p` 的设备在
  video m-line 上写的是 `a=rtpmap:8 PCMA/8000`（音频时钟），照抄会把 25 fps 的流
  算成 2.22 fps。MPEG-PS 的 PTS 单位由容器规范固定，与 rtpmap 无关。
- **同一路 PS 里会混有音频 PES**（`ps_h265_1080p` 有 646 个，stream_id `0xC0`
  段）。解复用必须按长度跳过它们，只把 `0xE0..0xEF` 的载荷拼进视频访问单元；
  这份样本是第一份音频占比可观的真机流，正好验证了这条路径。

## 第一次全量摸底（42 台在线摄像机）

一次性对同一分组下 59 台设备中 `is_online=1` 的 42 台逐台取播放链接并当场采集
（token 分钟级过期，只能取一台采一台）：

| | 结果 |
| --- | --- |
| 出流成功 | 39 |
| 服务端报错 `26214462` | 3（`is_online=1` 但取不到流，客户端已正常上报并断开） |
| 容器 | 39 / 39 都是 PS |
| 编码 | H.264 20 台、H.265 19 台 |
| 分辨率 | 39 / 39 都是 1920x1080 |
| fps | 24.5 ~ 25.0 |
| SDP `paramsets` | 39 / 39 为 0，分辨率全部靠码流内 SPS 还原 |

结论：**MEDIAINFO 从不带参数集，从码流还原 SPS 不是兜底路径而是主路径**；同一批
设备里 H.264 和 H.265 各占一半，两条编码分支都必须是一等公民。

`26214462` 不在客户端已知错误码表里，`h5player.min.js` 里也查不到，属于服务端侧
的取流失败，客户端无需处理——它已经通过 `OnError` 上报并结束会话。

## RTP 二次封装（`ps_h264_720p` 实测）

**不是所有设备都直接发裸 PS。** 这台设备把每个 PS 分片再套一层 RTP：WebSocket
消息以 `80 60 ...` 开头（version 2、PT 96），2031 个包里 1728 个带 padding、
1886 个带 marker、SSRC 全程为同一个值，无 CSRC、无扩展头。

危险在于**症状完全不可见**：把 RTP 头留在载荷里，PS 解复用器靠 resync 依然能跑
出 655 帧 / 26 关键帧 / 1280x720，和正确结果一模一样。只有对基本流做 sha256
才发现两者从 offset 8054 起就不同——145 个包中段的 RTP 头被当成图像数据写进了
PES 载荷，画面是坏的而计数是对的。

判定用的是**严格 PS 结构走查**（只按规范逐个 pack/system/PSM/PES 前进，不允许
任何 resync）：

| 处理方式 | 走查结果 |
| --- | --- |
| 原样（RTP 头在内） | offset 0 即脱轨 |
| 只剥 12 字节固定头 | 走到 51587 脱轨 |
| **剥固定头 + 尾部 padding** | **走到文件尾，2671 个元素** |

2671 = 655 pack + 52 system + 52 PSM + 655 视频 PES + 1257 音频 PES。
只有两者都剥才字节级正确，所以 `rtp.go` 的 `rtpPayload` 两件都做（并按规范处理
CSRC 列表与扩展头长度）。padding 计数是最后一个字节且**含自身**，越界就说明这
根本不是 RTP，此时原样返回，裸 PS / 裸 annex-b 才不会被误剥。

归档的 `stream.ps` 是**去封装后**的干净 MPEG-PS（4,053,224 字节，`ffprobe` 可直
接读）：RTP 是传输层的事，样本要留的是容器层的真相。

### 逐消息判 RTP 是错的：必须整条会话只判一次

上面这套剥离逻辑最初是**逐条消息**执行的：每收到一条二进制消息就看首字节高两位
是不是 `0b10`（RTP version 2），是就剥。在裸 PS 的设备上这条判断会误伤——裸 PS
的续传消息从任意字节开始，**任意字节有 1/4 的概率高两位是 `0b10`**，于是大约每
四条消息就有一条被砍掉 12 字节头，还可能按最后一字节再砍掉一段"padding"。

42 台在线摄像机实测，39 台成功出流，**39 份采集全部在严格结构走查里脱轨**；而帧
数、关键帧数、分辨率、fps 全部正常——症状再一次完全不可见。

判定必须**整条会话只做一次，且用两条连续消息互证**：SSRC（byte 8-11）相同，且序
号（byte 2-3）正好 +1。单条消息提供的信息量不足以区分 RTP 头和视频数据，两条连
续消息才够。第一条消息因此暂存到第二条到达后一起下发；会话若只有一条消息，在
flush 时原样放行。修复后同样 42 台复测：

| | 逐消息判定 | 会话级两条互证 |
| --- | --- | --- |
| 严格走查脱轨 | 39 / 39 | **0 / 39** |

（其中 2 份的最后一个元素被采集时长截断，属于停止采集的正常现象，不是数据损坏。）

## 直播是从流中间接进去的：前导残帧必须丢

实测 42 台里有 **7 台**的第一条消息落在某个访问单元中间——最极端的一台在见到第
一个 pack 头之前已经收了 151KiB，那是一个关键帧的尾巴。这些字节的头我们从未收
到，拼出来是个解不了的残帧，而且它自带 PTS，会让首帧时间戳偏早。

所以解复用器在**见到第一个 pack 头之前不收 PES**（`psDemuxer.synced`）。这不影响
从 pack 头开始的流：那种流在第一个 pack 处的累积缓冲本来就是空的。

严格走查同理，起点要取**第一个起始码**而不是文件 offset 0，末尾要容忍最后一个元
素被截断——否则会把"从流中间接入"和"采集到时间就停"这两件正常的事误判成损坏。

## 第二次全量摸底（123 台在线摄像机，全量设备表）

第一次只覆盖了一个分组的 42 台。这次拉了完整设备表（435 台，其中 `is_online=1`
的 123 台），逐台取链接、当场采集 8 秒：

| | 结果 |
| --- | --- |
| 出流成功 | **94** |
| 服务端报错 / 超时 | 27（`26214462`×20、无数据超时×4、`26214476`×2、`26214475`×1） |
| 取不到播放链接 | 1 |
| **客户端崩溃** | **1**（`Unpack` 越界 panic，见下） |

出流的 94 台的形态分布：

| | 结果 |
| --- | --- |
| 容器 | 94 / 94 都是 PS（其中 1 台要靠修好的嗅探才认得出） |
| 编码 | H.264 54 台、H.265 40 台 |
| 分辨率 | 1920x1080 57 台、1280x720 37 台 |
| fps | 10.11 ~ 28.85 |
| 严格结构走查 | **92 干净 / 1 末元素被采集时长截断 / 0 脱轨** |
| 从流中间接入（首字节不是 pack 头） | 22 / 93 |

延迟（从 WebSocket 连上算起，94 台）：

| | min | p50 | p90 | max |
| --- | --- | --- | --- | --- |
| MEDIAINFO 到达 | 108ms | 235ms | 2749ms | 4361ms |
| 首帧解出 | 128ms | **450ms** | 2830ms | 4508ms |

p50 到 p90 差出一个数量级，且 `mediainfo` 与 `firstFrame` 几乎同步抬高——慢的是
服务端建流，不是客户端解析。客户端本身几乎不占时间：`firstFrame - firstByte` 的
中位数是 **29ms**、最大 182ms，就是等第二个 pack 头关帧那一帧的容器固有延迟。

### 这一轮摸出来的 5 个客户端缺陷

前四个都属于"数字全对、数据是坏的"那一类，只有全量真机才能撞出来：

| 缺陷 | 触发条件 | 症状 | 修法 |
| --- | --- | --- | --- |
| RTP 判定被首包分片打断 | 代理把第一个 RTP 包拆成 8192+12 两条消息 | 2 台 HVAG 设备被判成裸 PS，12 字节 RTP 头被拼进码流 | 判定改为在**前 4 条消息里找一对**互证的 RTP 头，而不是只看相邻两条 |
| MEDIAINFO 不可解时容器/时钟留空 | `HVAG` 头设备 | 容器为空、无 90kHz 时钟，PTS 推不出 fps | 嗅探到 PS 就把 `Container="PS"`、`ClockRate=90000` 写回 |
| H.264 `scaling_list()` 越读 | High profile 且缩放表提前终止（`delta_scale` 为 0） | 1 台 720p 设备分辨率恒为 0x0 | 按规范用 `lastScale/nextScale` 状态机跳表 |
| PS 嗅探只认 `00 00 01 ba` | 直播从音频 PES（`00 00 01 c0`）处接入 | 1 台设备整条会话被判成非 PS，原始传输块直接当帧下发 | 接受任意 PS 起始码（`>= 0xB9`） |
| `Unpack` 长度回绕 | 无协议信封的帧，长度字段是 `0xFFFFFFFB` | `5+length` 在 uint32 里回绕成 0，越过边界检查后 `data[5:0]` **panic，进程被打死** | 长度先扩成 `uint64` 再做边界检查 |

最后一个是这批里唯一能被远端字节直接打死进程的问题：长度字段来自网络，回绕检查
必须在**加法之前**就完成。前四个的共同点是——`isPSData`、RTP 判定、MEDIAINFO 解码
这些"一次性判定"都是在**会话最开始、信息最少的时候**做的，而直播恰恰是从流的任意
位置接进去的。凡是一次性判定，都要能容忍"我接进来的地方不是流的开头"。

## 多路并发实测（同一批 123 台在线设备，8 vCPU 容器）

前两轮摸的是"每一台能不能解对"，这一轮摸的是"同时拉 N 路要付多少代价"。工具是
`go-client/e2e/bench`（不落盘，只计数），**完整数据表、判据和复现方法见
`go-client/e2e/bench/README.md`**，这里只留结论：

| 问题 | 实测答案 |
| --- | --- |
| 单路成本 | CPU **0.0012~0.0023 核/(Mbit/s)**、RSS **0.3~0.65 MiB**、goroutine **4 个**（`AsyncDelivery>0`，否则 3 个）、带宽 440~1600 kbit/s |
| 上限是多少 | 本环境**约 40~48 路**；40 路时 50.98 Mbit/s 全员 25fps，48 路起有个体被饿到 0.52fps |
| 上限由什么决定 | **上游/网络带宽**，不是客户端。48/64/122/128 四次运行总吞吐都封在 53.2~53.5 Mbit/s，而 CPU 峰值只有 0.138/8 核、128 路 RSS 76 MiB、FD 约 130 |
| 掉帧怎么掉 | 过拐点后按路数均分带宽（64 路 834 kbit/s → 128 路 417 kbit/s），且**不均匀**：128 路均值 9.29fps 而最低 2.71fps。容量红线要看**最低 fps**，不是平均 fps |
| 同一台设备能并行吗 | **能**。同设备 6 个 token 同时拉，6/6 满帧、0 错误、结构走查 0 脱轨。并发上限不受在线设备数约束 |
| 并发下解析还对吗 | 64 路开严格结构走查：**64 checked / 0 derailed** |

据此做了两处纯内存优化（PS 访问单元缓冲复用、WebSocket 读缓冲复用），**不改变交付
给调用方的字节**：离线回放 −57% 分配 / −32% 耗时，线上 128 路分配速率 45.2 → 14.2
MB/s、窗口内 GC 136 → 21 次、CPU −26%。吞吐没变是对的——瓶颈在上游带宽。

## 0xBD 私有流里有什么（以及没有 PTZ 坐标）

问题是：码流里除了音视频，还有没有球机坐标 / 转动角度 / 定位这类可用信息。

把 94 份采集里的 `private_stream_1`（`00 00 01 bd`）全部拆出来，一共只有 4 种记录：

| 型 | 载荷长度 | 前 4 字节 | 条数 | 设备数 | 频率 |
| --- | --- | --- | --- | --- | --- |
| A | 96 | `00 02 00 17` | 434 | 82 / 94 | 约 1 条 / 秒 |
| B | 24 | `00 03 00 05` | 925 | 12 / 94 | 约 10 条 / 秒 |
| C | 92 | `00 08 00 16` | 45 | 1 / 94 | 约 6 条 / 秒 |
| D | 36 | `00 03 00 08` | 1 | 1 / 94 | 整队列只出现过一次 |

逐型看：

- **A 型是加密的，客户端拿不到内容。** 16 字节固定头
  `00 02 00 17 00 01 80 00 00 ff 00 00 e0 f1 f0 50`（末字节 `0x50` = 80 = 后续载荷
  长度），后面 80 字节每条都变、全是高熵字节。但 **434 / 434 条的第 3、4 个 16 字节
  块完全相同**——明文里有两个一样的 16 字节字段，密文也就一样，这是 16 字节分组
  密码 ECB 模式的特征。没有设备密钥就解不出，属于海康的私有帧信息 / 数字水印。
- **B 型是常量，不是遥测。** 12 台设备、925 条记录，
  `00030005 0001800000ff0000 ffff0401008187808438ff02` **一个字节都不变**，跨设备
  也完全相同。恒定的东西不可能是坐标或角度，它是一条能力 / 配置声明。
- **C 型是唯一带空间语义的，但只有 1 台设备发。** 明文，含 `c0 02 40 02`
  （小端 704 x 576，D1 坐标空间）和一个矩形 `20 00 20 00 16 00 12 00`。45 条里随
  时间变的只有 7 个字节，取值都是 `0/2/6`、`0/4/8`、`0/128`、`8/10/14` 这种位标志式
  的慢变量——像移动侦测 / 遮挡状态，但一台设备一次 8 秒采集不足以定义语义。
- **D 型只出现过一次**（`ps_h264_1080p` 样本里就有那一条），与 B 型共享
  `ffff 0401 ...87808438` 的骨架，样本量不足以分析。

**结论：码流里没有球机坐标、转动角度或定位信息。** 82 台设备发的 A 型是加密的，
覆盖面第二广的 B 型是常量，唯一带坐标空间的 C 型只有 1 台设备且不含位置。这与
`h5player.min.js` 的行为一致：官方播放器同样不解析 0xBD，PTZ 状态走的是设备的
ISAPI / HTTP 接口，不在码流里。

所以**不给组件加 `OnPrivateData` 回调**：4 种记录没有一种是调用方能用的，加了回调
只是把不可解的字节搬一层。真正要保证的是解复用器**跳过** 0xBD——它带自己的 PTS，
当成视频既会把 96 字节密文拼进码流、又会把帧的时间戳取错，而帧数、关键帧数一切
正常。`TestPSDemux_SkipsPrivateStream` 用真机采集的那条 0xBD 包守住这一点。

## 踩坑记录

- **自建 mock 要照着真实字节写。** 单元测试的构造 helper 一旦和实现犯同一个错误
  （PES 头长度取错位置），测试全绿而线上全错。涉及线格式的断言要手写字节，不要
  复用 helper。
- **"帧数对、关键帧对"不等于解析正确。** 上面的 PES 截断问题、RTP 头未剥问题，在
  摘要里都完全看不出来（后者连分辨率都是对的），只有对照 `ffprobe`、逐字节回放归档
  样本、或做严格结构走查才能发现。这正是要留样本的原因。
- **对一条消息做启发式判定，等于按概率破坏数据。** "首字节高两位是 10 就当 RTP"
  在单条消息上看着挺合理，摊到整条流上就是 1/4 的误判率。凡是要在两种线格式之
  间二选一，判定就必须建立在**跨消息的不变量**（SSRC 相同、序号连续）上，并且整
  条会话只判一次。
- **三份样本证明不了 39 台设备。** 仓库里的样本全绿，同一份代码在真机队列上却
  39/39 损坏——样本覆盖的是"见过的形态"，全量摸底覆盖的是"实际部署的形态"，两
  者都要跑。
- **SDP 只是提示，码流才是事实。** 前两台设备的 MEDIAINFO 能解，就默认了它总能解；
  第三台换成 `HVAG` 头，整条链路退化成"未知容器 + 未知编码"。凡是设备自报的元数据，
  都要有一条从码流本身推导的兜底路径。
- **一次连接只做一件事的工具设计是错的。** token 分钟级过期，"先分析再抓包"的两次
  运行第二次必然失败，白白烧掉一个链接。`probe` 因此把两件事合并进同一次连接。
- **42 台也证明不了 123 台。** 第一次摸底 42 台全绿的那份代码，扩到全量设备表就
  撞出 5 个缺陷，其中一个直接 panic。覆盖面每扩一档，就会遇到一档新的设备形态；
  "跑过一轮真机"不是一劳永逸的结论。
- **统计码流构成也必须走查，不能扫起始码。** 这份 README 自己警告过"PES 载荷里
  会出现伪起始码"，早先的 PES 计数却是扫 `00 00 01 xx` 数出来的，四份样本里有两份
  数错。用来找问题的工具，本身也得按规范逐元素前进。
- **来自网络的长度字段，回绕检查要在做加法之前。** `5+length` 先算再比大小，在
  uint32 里回绕成 0 就能骗过任何边界检查。一个字节的构造就能远端打死进程。
