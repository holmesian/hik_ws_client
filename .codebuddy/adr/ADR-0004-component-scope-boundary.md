# ADR-0004 组件边界——只做取流与解复用，不解码、不解密、不解析私有流、不做 PTZ

## 状态（Status）

`Accepted`（2026-08-01 由项目 owner 确认）——记录的是既成边界。

## 背景与问题（Context）

优化过程中反复出现"顺手把这个也做了"的候选，逐一评估后都没有做，理由需要固化下来，否则
下一轮会重新讨论一遍，或被某个 agent 直接实现出一段无法验证的推测代码：

- **媒体解密**：协议里定义了 `EncryptFlag`(0x80)，但 realplay 以空 key 请求，服务端不下发
  加密流——媒体载荷本身不加密，密钥交换只用于会话鉴权。实现解密属无场景的推测代码。
- **`0xBD` 私有流**：94 台普查共 4 种记录。A 型（82 台）是 ECB 加密的，无设备密钥无法验证
  内容；B 型（12 台）跨设备跨时间**一个字节都不变**，是能力声明；C 型只有 1 台设备且不含
  位置；D 型全队列只出现一次。**没有球机坐标、转动角度或定位信息**，与 `h5player.min.js`
  的行为一致（官方播放器同样不解析 0xBD，PTZ 走设备 ISAPI/HTTP 接口）。
- **解码**：`python-client/play.py` / `go-client/screenshot.go` 都是把访问单元原样喂 ffmpeg，
  本仓库不内置解码器。
- **音频**：音频消息原样下发，未解 PES、未解码，目前无下游需求。
- **云台可观测性**：上面的 `0xBD` 结论来自静置普查。补做的受控差分实测（转动期间实时抓同一
  条流，19 次采集 / 64 次转动 / 8 次静置对照）进一步确认：WS 文本、WS 二进制未知类型、`0xBD`、
  码流内 SEI 四层在转动窗口内外**零变化**；唯一有信号的编码器间接层（P 帧膨胀）测的是**场景
  变化**而非云台状态——静置对照组的自然场景事件（54.5x）比 64 次真实转动的最强扰动（38.6x）
  还大，物理上分不开"云台在转"与"有人从镜头前走过"。想知道方位只能问设备控制接口，码流侧
  做不到。把这层信号包装成 `IsPanning()` 会给调用方一个约 30% 漏报、每分钟一次误报的假承诺。

## 决策（Decision）

我们决定：**组件的职责边界是"把传输字节还原成可直接喂解码器的 Annex-B 访问单元"，止步于此。**

- 不实现媒体解密；`EncryptFlag` 仅解析并暴露，不据此解密。
- 不解析 `0xBD` 私有流，也**不为它加回调**——把不可解的字节搬一层没有价值；解复用器必须
  跳过它（它自带 PTS，当视频处理会同时污染码流和时间戳）。
- 不内置解码器；`VideoSaver` 之类的工具依赖外部 ffmpeg，属可选设施。
- 不提供 PTZ / 云台能力；需要方位信息的调用方走设备独立控制接口。
- 音频保持原样下发；确有需求时另开 ADR。

## 后果（Consequences）

**正面**：组件小、依赖少、可测；不产生无法验证的推测代码；调用方对能力边界有明确预期。

**负面 / 风险**：需要云台信息或音频解码的场景必须另找通道，本组件不提供。若将来出现真正
下发加密流的部署形态，本决策需重新评审。

**合规要求**：越过上述边界的功能一律先开 ADR。禁止"因为协议里定义了所以实现一下"——
本项目已有多处这种常量被证明只是文档遗留。
