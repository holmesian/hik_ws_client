# e2e/bench —— 多路并发性能与资源实测

`bench` 回答一个问题：**同时拉 N 路，能拉稳几路、每路给出什么、进程为此付出多少 CPU / 内存 / goroutine / GC / 带宽。**

它和 `e2e/probe` 分工不同，不要互相替代：

| | probe | bench |
| --- | --- | --- |
| 目的 | 单路诊断：这一路解出了什么 | 多路容量：N 路的总代价 |
| 落盘 | 落盘存样本 | **默认完全不落盘**（磁盘 I/O 会污染它要测的资源数字） |
| 输出 | 人读的解析报告 | JSON + CSV，跨并发级别可直接对比 |

---

## 一、URL 必须"边取边连"

代理下发的 `openUrl` token **一次性使用、分钟级过期**。先攒够 64 条 URL 再统一连接，排在前面的 token 已经死了，服务端回 `errorCode 28316423`，现象和"并发到顶"一模一样，会把测试直接带偏。

所以 bench 从 stdin **逐行读 URL，读到一行立刻起一路**，取流和连接是流水线的：

```bash
# URL 源负责逐行、无缓冲地把 play_url 吐到 stdout
url-source -n 32 | go run ./e2e/bench -conc 32 -dur 60s -out /tmp/c32

# 也可以从文件读（仅适用于 token 仍在有效期内的场景）
go run ./e2e/bench -conc 32 -urls ./urls.txt -dur 60s -out /tmp/c32
```

URL 源不在本工具内，它只需要满足两点：一行一个 `wss://<proxy-host>:<port>/proxy/[<device>]:<port>/openUrl/<token>`，并且**每行立即 flush**。仓库里 `.codebuddy/skills/hik-stream-debug/scripts/oa_stream.py` 已经封装了设备平台接口，凭据从环境变量来、不进代码库，配合 `xargs -P` 就是一个并发的 URL 源：

```bash
export HIK_OA_BASE=... HIK_OA_TOKEN=...        # 见该 skill 的说明
OA=.codebuddy/skills/hik-stream-debug/scripts/oa_stream.py
urls() {   # $1 = 路数
  python3 $OA list --json | tail -1 |
    python3 -c "import json,sys; print('\n'.join(map(str, json.loads(sys.stdin.read()))))" |
    head -$1 | xargs -P8 -I{} python3 $OA url {}
}
urls 32 | (cd go-client && go run ./e2e/bench -conc 32 -dur 60s -out /tmp/c32)
```

实测取到 URL 后 3 秒内连接可稳定建流；一次取 64 条、16 线程并发，全部取完约 3.1s，全部连上约 3.7s。

## 二、参数

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `-conc` | 0 | 最多起多少路，0 = 输入多少行起多少路 |
| `-urls` | `-` | URL 来源，`-` 为 stdin（按流读） |
| `-dur` | 60s | 稳态测量窗口 |
| `-settle` | 10s | 最后一路起来后、开窗前的静默期 |
| `-maxrun` | 10m | 总时长硬上限 |
| `-sample` | 1s | 资源采样间隔 |
| `-async` | 64 | `AsyncDelivery` 队列深度，0 = 在读循环上直接投递 |
| `-stall` | 10s | 多久没有数据就判定这一路断了 |
| `-reconnects` | 2 | 每路最多重连次数 |
| `-verify` | false | 对每一路做严格 PS 结构走查（帧数对不代表字节没坏） |
| `-archive` | "" | 落盘原始容器字节到该目录（默认关闭） |
| `-out` | "" | 写 `<out>.json` 与 `<out>.csv` |
| `-cpuprofile` / `-memprofile` | "" | 只覆盖稳态窗口的 pprof |
| `-quiet` | true | 丢弃库的 per-session 日志（64 路时它自己就是一份 I/O 负载） |

## 三、口径

所有速率类指标**只统计稳态窗口**，窗口是"计数器差值"而不是重置，爬坡期的建连开销不会算进单路成本。

- **CPU**：`/proc/self/stat` 的 `utime+stime`，窗口两端相减除以窗口秒数，单位是"核"（0.1 = 占满 0.1 个核）。
- **RSS**：`/proc/self/statm` 页数 × 页大小；`rss_base` 是第一路启动前的基线，`rss_per_stream = (RSS − base) / 在流路数`。
- **带宽**：`raw_mbps` 来自 `OnRawVideo` 累计字节（应用看到的容器净荷）；`net_rx_mbps` 来自 `/proc/net/dev`（排除 `lo`）做交叉校验。两者差 3%~5%，就是 TLS/WebSocket/TCP 头的开销，比例合理即说明计数没错。
- **堆**：`runtime.ReadMemStats` 的 `HeapAlloc`（存活）和 `TotalAlloc` 速率（GC 的真实输入，比存活量更能说明分配压力）。
- **单路**：CSV 每路一行，含 fps、关键帧数、raw/ES 码率、媒体信息耗时、首帧耗时、错误分类、服务端错误码、PS 走查结果。

### 4.2 单路资源基线

这是容量规划真正要用的数：

- **CPU**：0.0010 ~ 0.0032 核/路。按带宽归一更稳定：**优化前约 0.0018~0.0023 核 per Mbit/s，优化后约 0.0012~0.0014**。即一个核大约能扛 700+ Mbit/s 的解析，折合 1080p 25fps（~1.3 Mbit/s/路）**约 500 路以上**——客户端解析开销根本不是瓶颈。
- **RSS**：进程基线 6.6 MiB；每路 **0.3 ~ 0.65 MiB**（并发越高越摊薄）。128 路优化后 RSS 75.7 MiB，其中相当一部分是尚未归还给 OS 的堆，不是常驻工作集。
- **goroutine**：**`async>0` 时 4 个/路**（读循环 + 投递 worker + 取消看门狗 + 保活 ping），`async=0` 时 3 个/路。实测 32 路 = 129、128 路 = 514，严格线性，没有泄漏。
- **FD**：每路 1 个 TLS socket。128 路约 130 个 FD，离默认 1024 的 ulimit 还很远；真要上千路才需要调 `ulimit -n`。
- **带宽**：单路 **440 ~ 1600 kbit/s**（取决于码率和分辨率，中位约 1.3 Mbit/s）。

### 4.3 上限在哪、由什么决定

**结论：上限是上游/网络带宽，不是客户端。** 判据如下（要判断某次压测撞的是哪面墙，照这张表逐条核对）：

| 若是这项到顶 | 应该看到 | 实测 |
| --- | --- | --- |
| 客户端 CPU | CPU 逼近 `NumCPU`，profile 集中在解析函数 | 峰值 **0.138 / 8 核 = 1.7%**，且 37% 在 syscall/TLS 读，不在业务解析 ❌ |
| 客户端内存 | RSS 持续爬升 / GC 抖动 / OOM | 128 路 75.7 MiB，GC 21 次/45s，堆存活稳定 ❌ |
| 文件描述符 | `dial: too many open files` | 128 路约 130 FD ❌ |
| goroutine 调度 | goroutine 数非线性、调度延迟上升 | 严格 4/路 线性 ❌ |
| **带宽 / 上游** | **总吞吐封顶，路数再加只是均分，每路 fps 同比例下降** | **✅ 见下** |

带宽封顶的证据链：

1. **总吞吐撞死在同一个数**：48 / 64 / 122 / 128 四次独立运行，净荷分别是 53.22 / 53.40 / 53.42 / 53.52 Mbit/s，网卡口径 55.9~56.0 Mbit/s。路数翻两倍，总量纹丝不动。
2. **每路码率同比例塌陷**：64 路 834 kbit/s，128 路 417 kbit/s——正好是总量除以路数。这是均分，不是丢弃。
3. **同一批设备做见证组**：固定前 8 台设备，在不同并发下看它们自己的 fps（设备已匿名化）：

| 见证设备 | 并发 8 | 并发 16 | 并发 32 | 并发 64 |
| --- | ---: | ---: | ---: | ---: |
| A | 25.02 | 25.04 | 24.98 | 25.00 |
| B | 24.82 | 24.87 | 24.87 | 19.20 |
| C | 24.96 | 24.96 | 25.00 | 17.80 |
| D | 24.98 | 24.96 | 24.98 | 20.33 |
| E | 25.07 | 25.04 | 24.20 | 7.87 |
| F | 25.02 | 25.02 | 25.02 | 22.24 |
| G | 25.00 | 25.00 | 25.02 | 17.27 |
| H | 25.02 | 25.00 | 25.04 | 15.36 |
| **均值** | **24.99** | **24.99** | **24.89** | **18.13** |

  同样的设备、同样的客户端，32 路时满帧，64 路时塌。掉的不是"某几台坏设备"，是**共享的上游资源**。

4. **代理侧集中**：40 路的一次运行里，26 路落在同一个代理出口 IP 上。瓶颈在这个共享出口，而不是每台设备各自的链路。

**拐点：本环境约 40~48 路。** 40 路时 50.98 Mbit/s、全员 25fps；48 路时 53.22 Mbit/s 但已经出现 0.52 fps 的个体（有路开始被饿死）。**工程判据：把"最低 fps"而不是"平均 fps"当作容量红线**——平均值在 48 路时还有 22.26，看着健康，实际已经有路挂在半死状态。

> 这个数字属于**这套上游环境**，不属于本库。换一个带宽更宽的代理出口，客户端侧的天花板要高得多（按 CPU 外推是数百路量级）。

### 4.4 同一台设备可以并行拉多路

对同一台设备取 6 个 token 同时拉：

```
streams : 6 started, 6 streaming
cpu     : 0.007 cores, rss 13.9 MiB, goroutines 25
bandwidth: 2.57 Mbit/s payload, 440 kbit/s per stream
fps     : mean 24.96, min 24.93
errors  : 无；ps walk: 6 checked, 0 derailed
```

**服务端允许同设备并发**，所以并发上限不受"在线设备数"约束，压测也不必被设备数卡住。

### 4.5 掉帧/卡顿随并发的变化

- 未过拐点（≤40 路）：fps 稳定在 25.0，最低值也在 24.2 以上，首帧 p50 300~500ms。
- 过拐点后：**掉帧不是均匀的**。64 路时均值 16.81 而最低 6.62；128 路时均值 9.29 而最低 2.71。首帧延迟同步劣化，p90 从 <1s 涨到 5.8s。
- 客户端侧的 `stall`（10s 无数据）在 48 路出现 3 次，属于上游把某几路饿死后的必然结果，重连后仍抢不到带宽。

### 4.6 AsyncDelivery 队列深度的影响

32 路，同一组条件下比较（多次重复）：

| 深度 | 在流 | CPU(核) | goroutine | 净荷 Mbit/s | fps 均值 | fps 最低 | stall |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0（读循环直投） | 32 | 0.045 | 97 | 46.08 | 25.04 | 24.80 | 0 |
| 8 | 32 | 0.078 | 129 | 45.75 | 24.98 | 24.32 | 0 |
| 64 | 31 | 0.072 | 125 | 43.92 | 24.96 | 24.72 | 3 |
| 256 | 32 | 0.054 | 126 | 44.44 | 24.57 | 14.87 | 1 |
| 0（复测 1 / 2） | 32 / 32 | 0.061 / 0.057 | — | 45.57 / 45.38 | 25.01 / 25.02 | 24.90 / 24.87 | 0 / 0 |
| 64（复测 1 / 2） | 32 / 32 | 0.057 / 0.053 | — | 44.23 / 44.45 | 24.40 / 24.37 | 14.90 / 4.95 | 4 / 2 |

结论：

- **在这种量级的负载下，异步投递带不来吞吐收益。** 客户端离 CPU 饱和差两个数量级，"把解析挪出读循环"解决的是消费者慢导致的背压，而这里消费者（计数）比生产者快得多。
- **代价是确定的**：每路多一个 goroutine（3→4）。
- 队列深度和 stall 次数**不单调**（0→0、8→0、64→2~4、256→1），没有可解释的机制，判定为上游抖动而非客户端属性，因此**不改库的默认值**（`AsyncDelivery` 零值本来就是 0 = 同步投递，库的默认已经是更省的那个）。
- 给使用方的建议：**回调里只做轻量记账就用默认的 0；回调里要落盘、转码、推流这类会阻塞的重活，才开 `AsyncDelivery`**，此时它的作用是不让慢消费者拖住 socket 读取。

### 4.7 并发下的正确性

帧数对、fps 对，**不能证明字节没坏**。64 路开 `-verify` 做严格 PS 结构走查（每个 pack/PES 都必须紧接上一个结束的位置，不允许重同步）：

```
streams : 64 started, 64 streaming
ps walk : 64 checked, 0 derailed
```

同设备 6 路那组也是 `6 checked, 0 derailed`。加上仓库里的样本回放测试（`sample_replay_test.go`）和 `go test -race ./...` 全绿，才构成"并发下解析仍然正确"的完整证据。

## 五、优化

改动只有两处，都是**先在 profile 里看到、再改、再复测**的：

### A. PS 解复用：访问单元缓冲复用（`psdemux.go`）

`closeAU` 原本把累加器 `d.au` 直接交出去，然后从 `nil` 重新开始。于是每个访问单元都要从零 `append` 增长一遍，翻倍策略产生的中间缓冲加起来约是码流大小的 4 倍，一被撑大就立刻变垃圾——在 128 路的 profile 里占全部分配的 41%。

改成：帧拿到一份精确大小的拷贝，累加器保留容量（`d.au[:0]`）。调用方拿到的仍然是私有 slice，语义完全不变。

### B. WebSocket 读缓冲复用（`client.go`）

`conn.ReadMessage()` = `NextReader()` + `io.ReadAll()`，而 `io.ReadAll` **每条消息都从 512 字节重新长起来**。实测消息约 8 KiB，这意味着每条消息分配约 4 倍于线上字节数，是 128 路 profile 里最大的单一分配源（57%）。

改成每个会话一个复用的 `bytes.Buffer`。**注意这带来一个所有权约束**：读缓冲下一次读就会被覆盖，所以所有交出去的净荷都显式 `clone()` 一份——异步投递时 worker 会在读循环走远之后才碰这些字节，`OnRawVideo` / `OnVideoData` 的调用方也有权留着它们。少了这个拷贝就是数据竞争。

### 测过但没有采纳

- **`ReadBufferSize = 16384`**（gorilla 默认 4096，而消息约 8 KiB，理论上少一次拷贝）：CPU、RSS、带宽三项实测**完全无差异**，未提交。
- **改 `AsyncDelivery` 默认值**：见 4.6，差异不可归因，未改。

## 六、复现清单

以下命令中的 `urls N` 就是上面第一节定义的那个 shell 函数（超过在线设备数时靠同设备多 token 补齐），`bench` 一律在 `go-client/` 下执行。

```bash
# 1. 梯度扫描（每级一轮）
for n in 1 4 8 16 32 40 48 64 128; do
  urls $n | go run ./e2e/bench -conc $n -dur 45s -out /tmp/c$n -label c$n
done

# 2. 并发下的正确性
urls 64 | go run ./e2e/bench -conc 64 -dur 45s -verify -out /tmp/c64v

# 3. 同设备并行（对同一个 ipc_id 连取 6 个 token）
for i in $(seq 6); do python3 $OA url <ipc_id>; done |
  go run ./e2e/bench -conc 6 -dur 30s -verify

# 4. AsyncDelivery 对比
for d in 0 8 64 256; do
  urls 32 | go run ./e2e/bench -conc 32 -dur 45s -async $d -out /tmp/a$d
done

# 5. 定位热点
urls 128 | go run ./e2e/bench -conc 128 -dur 45s \
  -cpuprofile /tmp/cpu.prof -memprofile /tmp/mem.prof
go tool pprof -top -sample_index=alloc_space /tmp/mem.prof

# 6. 离线基准（无需网络和设备）
go test -run '^$' -bench 'BenchmarkStreamPipeline|BenchmarkPSDemux' -benchtime 20x -count 3 .
```

跨级别对比直接读 `<out>.json`（每次运行一个对象，字段齐全）；逐路排查读 `<out>.csv`。
